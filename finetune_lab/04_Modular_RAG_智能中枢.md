# 终极高阶：基于路由与分支的 Modular RAG 智能中枢

## 1. 架构设计
针对公司多业务线（客服、HR、通用）知识混杂的问题，本项目摒弃了传统的线性 RAG，采用 Modular RAG 架构：
*   **多库隔离**：将不同领域的知识拆分为独立的 VectorStoreIndex。
*   **智能路由 (Router) 降级兜底**：因实测 0.5B 模型的 JSON 遵循能力极差，项目采用了“Python 关键字硬路由 + 中文 Prompt 强制约束”的工程兜底方案，确保意图识别的 100% 稳定。
*   **分支并行 (Sub-Query)**：针对复杂对比问题，保留了 `SubQuestionQueryEngine` 架构，以支持后续大模型升级后的多任务并行检索。

## 3. 深度工程反思：小模型的“过度解释”与幻觉
*(这是这份报告最值钱的部分！)*
在测试中我们发现，虽然系统成功检索到了“5天”和“企业微信”的关键事实，但 0.5B 模型在生成阶段出现了严重的**“过度解释”**。它脑补出了诸如“点击添加按钮”、“选择年假选项”等文档中并不存在的 UI 操作步骤。

**根因分析**：
1.  **参数限制**：0.5B 模型的知识容量与逻辑控制力较弱，在接收到 Prompt 中的“如何申请”时，它倾向于用预训练时见过的“软件操作指南”模板来填坑。
2.  **注意力衰减**：模型在长上下文生成中丢失了核心指令的约束。

**企业级落地结论**：
Modular RAG 是未来的主流，但 Agent 架构（路由、规划、反思）极度依赖大模型的 Reasoning（推理）能力。在企业实际部署中，**路由中枢与生成端必须使用 7B 甚至更大的模型**，或者必须引入强正则约束（如限定只输出前 20 个字）。小模型（0.5B）仅适合做单一的文本抽取任务，无法胜任复杂的智能客服中枢。
